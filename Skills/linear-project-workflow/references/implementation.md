# 実装

## 着手と担当

実装開始の指示、承認済みの計画、依存関係、人間レビューの方針を確認し、着手可能な作業から進める。再開時も既存の指示を引き継ぎ、承認済みの計画レビューをやり直さない。

小さな作業や直接担当するよう指示された作業は、オーケストレーター自身が実装・検証する。独立した並行作業や専門的な調査など、分離する利点がある場合はWorkerへ委任する。

Workerへ委任する際は、作業の複雑さ、不確実性、失敗時の影響に応じて、利用可能なモデルとReasoningを選ぶ。人間の指定があれば優先する。選択は実行時に判断し、Issueごとの難易度評価や選定理由の記入を必須にしない。

Workerには目的、担当・変更範囲、参照先、完了条件、検証観点、人間レビューの条件を渡す。毎Issueの新規起動や担当交代は必須にせず、関連作業は同じWorkerが継続できる。並行作業では変更範囲と依存関係を調整する。

Workerは結果・検証・残件を報告し、担当範囲を超える判断はオーケストレーターへ戻す。オーケストレーターは成果と検証の根拠を確認し、計画との整合とLinearへの反映に責任を持つ。

## 計画変更

- 合意した目的・範囲・完了条件の内側なら、必要なIssueの追加・分割、依存関係、作業順を自律的に調整して報告する。独立して管理する意味のある作業をIssueにし、細かな実装手順までIssue化しない。
- 目的・範囲・完了条件を変える場合は、変更案と影響をチャットで示し、人間のレビュー後に反映する。完了扱いにするために条件を緩めない。
- 全体の進捗や次の作業に影響する変更は、Project Updateにも内容と理由を残す。

## 報連相と状態更新

報告と承認依頼を区別する。進捗、発見、失敗、復旧方針を伝えながら、継続できる作業は進める。人間の判断待ちでも、その回答に依存しない作業を進める。

| 記録先 | 内容 |
| --- | --- |
| チャット | 作業中の報告、人間の判断やレビューが必要な相談 |
| Issue | 個別作業の状態。コメントに結果の要約、検証内容、残る条件、成果物へのリンク |
| Project Document | 複数タスクで継続して参照する決定事項・設計・手順 |
| Project Update | 全体の進捗、重要な計画変更と理由、障害、次に進めること |

### Issueの状態

対象チームで使われている状態と意味を確認し、着手、レビュー待ち、作業停止、再開、完了の節目で更新する。内部レビューと外部レビューなどの違いも実際の運用に合わせる。

停止・保留には理由と再開条件を残す。実装が終わっても、必要な検証や合意した人間レビューが残っていれば完了にしない。

### Projectの状態とUpdate

全体の状況を捉え直す必要がある節目で、Projectの状態とProject Updateを更新する。個々の操作や毎Issueの完了を、新規投稿の必須条件にはしない。

1. 関連Issueの最新状態と結果を確認する。
2. Projectの現在地、残作業、保留理由、次の対応を整理し、状態が合うように更新する。
3. 直近の投稿への補足・訂正は既存投稿を編集し、新たな節目の報告は新規投稿にする。過去の経緯を現在の状態へ一律に書き換えない。
4. 保存結果を確認し、最新の報告に解決済みの事項が未解決として残っていないか照合する。

Issueの完了だけで論点の解決を決めず、別のIssueやProject全体に残る条件があれば明示する。Descriptionの目的・方針にも変更が及ぶ場合は、計画変更の条件に従って追従させる。

合意した運用内の状態・進捗更新は、毎回の承認を待たずに行う。書き込みに失敗した場合は、未反映の内容を報告し、通常の方法で復旧を試みる。結果不明の作成操作は既存投稿・Issueを確認してから再試行し、重複を避ける。同期できたと装わず、継続可能な作業は進める。

既存Project Updateの編集は、利用できるLinearツールで対象の更新IDを取得し、そのIDを指定して保存する。`get_status_updates` と `save_status_update` がある環境では、この組み合わせを使い、再取得して反映を確認する。

## 検証と完了

Issueの性質と完了条件に応じて検証し、実施結果と未確認事項を記録する。人間レビューが必要なら、確認できる成果と検証結果をそろえて提示する。

決定・設計・整理の成果は [作業結果の記録先](templates.md#作業結果の記録先) に従って反映し、後続作業から参照できることを確認する。Issue Descriptionへ成果の本文を追記せず、完了コメントに要約とリンクを残す。

Issueは完了条件、必要な検証、合意した人間レビューを満たした時点で完了にする。コミットなどの扱いは依頼と対象リポジトリの方針に従い、Workerの固定工程にはしない。

ProjectはIssueの状態に加え、全体の成功条件を確認する。残件が今回の完了を妨げるものか、合意済みの後続作業かを明確にする。Issueを設けていないProjectも同じ基準で確認する。

Issue・Projectの状態とProject Updateを整え、結果、検証内容、残る事項をチャットで報告する。
