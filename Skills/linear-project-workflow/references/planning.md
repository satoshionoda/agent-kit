# 計画

## 前提を調べる

対象Project、既存Issue、関連資料、実装状況を確認する。目的・成功条件・対象範囲・制約・主要方針と、未決定事項を整理する。

参照できる情報は自分で調べ、計画を左右する論点を人間と詰める。推奨案と判断理由を添え、一度に判断しやすい単位で相談する。軽微な判断まで確認事項にしない。

## Descriptionをレビューする

1. [書式](templates.md) を参照し、Description案をチャットに提示する。
2. 人間のレビューを受け、チャットで修正を重ねる。
3. 承認された内容をLinearへ反映し、そのままIssue設計へ進む。Issue設計の開始確認は挟まない。

Descriptionは目的・成功条件・範囲・方針を把握する入口にする。複数タスクで継続して参照する詳細や判断理由はProject Documentへまとめ、その草案もチャットでレビューする。同じ内容を扱うDocumentがあれば更新し、新設は独立して参照する必要がある場合に限る。

## Issueを設計する

- 独立して着手・完了を判断できる成果や作業をIssueにし、対象Projectへ所属させる。
- 完了条件、検証観点、依存関係、推奨順を整理する。人間にも作業の意味が分かる粒度を優先し、AIの担当分割に合わせた細分化を避ける。
- 小さなProjectはIssueなしでも進められる。大きすぎるIssueや複雑な子Issue群は、成果の分け方やProjectの範囲から見直す。
- 既存Issueがある場合は、追加・更新・分割などの変更点を示す。既存の進捗や人間の記録を保つ。
- 決定・設計・整理の成果を後続作業で使う場合は、記録先と参照先への反映を完了条件に含める。記録先は [書式](templates.md#作業結果の記録先) に従う。

Issue案をチャットで提示し、人間のレビュー後にLinearへ反映する。設計中にDescriptionの目的・成功条件・範囲・主要方針の変更が必要になった場合は、変更点と理由を示してレビューを受ける。

反映後は作成・更新したIssueと依存関係を確認し、Descriptionから参照できるようにする。承認済みの構成に実際のIssueリンクを付けるための追加承認は不要。

## 計画から実装への移行

計画の反映結果、次の着手先、実装を妨げる未決定事項を短く報告する。実装開始の指示がなければ待つ。

実装開始時の人間レビュー方針は、Issueごと、画面・重要判断のみ、節目ごと、検証後の完了報告など、指示された内容を記録する。未指定でも再確認を繰り返さず、完了判断や進行に必要な点だけ相談する。
