# 書式と記録先

計画の草案はチャットでレビューする。文章の構成と表現は [Writing Tune](../../writing-tune/SKILL.md) に従う。

## 共通方針

人間が内容を把握し、着手・判断・完了確認に使う情報を簡潔に書く。以下は項目の候補であり、すべて埋めるチェックリストではない。

- 必要な項目を選び、見出しの名称・数・順序を内容に合わせる。該当しない項目は省く。
- 短い内容は「対象と作業順」のようにまとめる。異なる論点が長くなる場合は分ける。冒頭の説明で目的が伝わるなら、目的の見出しは不要。
- 情報のまとまりを見出しで分け、並列事項は箇条書き、順序のある作業は番号付きリストにする。理由や関係の説明は短い段落でつなぐ。
- 自明な説明、同じ内容の言い換え、判断に影響しない補足を省く。関連資料の詳細はリンク先に任せ、その場に必要な要点だけを書く。
- 書いた後に読み直し、削っても理解や判断が変わらない文を削る。重要な条件・制約・未決定事項は残す。

## Project Description

目的と計画を把握する入口。見出しの有無によらず、目的・成功条件・対象範囲が読み取れるようにする。

| 項目の候補 | 内容 |
| --- | --- |
| 目的・背景 | 実現する成果と、その必要性 |
| 成功条件 | Project全体の完了を判断できる結果 |
| 対象範囲・対象外 | 今回扱う範囲と境界 |
| 主要方針・制約 | 全体に関わる進め方と守る条件 |
| Issue構成・作業順 | 作業の分担と依存関係の概要 |
| 未決定事項 | 計画を左右する未解決の論点 |
| 参照資料 | Project Documentsや関連資料へのリンク |

Issue設計前は構成を確定済みと扱わず、設計・承認後に実際のIssueリンクを反映する。進捗の経緯はProject Update、個別作業の詳細はIssueへ記録する。

## Project Document

複数タスクで継続して参照する決定事項・設計・手順をまとめる。同じ内容を扱うDocumentがあれば更新し、独立して参照する必要がある内容なら新しく作る。

| 項目の候補 | 内容 |
| --- | --- |
| 目的・適用範囲 | 何を扱い、どこで使う文書か |
| 決定事項・仕様・構成 | 後続作業で参照する具体的な内容 |
| 判断理由 | 選択の背景や重要なトレードオフ |
| 手順・判断基準 | 実施方法と条件による扱いの違い |
| 制約・注意点 | 利用時に守る条件や影響 |
| 未決定事項 | 確定内容と区別すべき論点 |
| 関連Issue・参照先 | 適用先や判断の経緯へのリンク |

構成や設定の対応関係には表を使うなど、文書の内容に合う構造を選ぶ。一時的な進捗・結果報告はProject Updateにまとめ、IssueやUpdateへ決定事項の全文を重複させない。

## Issue Description

何を実現し、どこまで行い、何をもって完了とするかが読み取れるようにする。タイトルは本文と分けて設定する。

| 項目の候補 | 内容 |
| --- | --- |
| 目的・背景 | 実現したいこと、作業が必要な理由 |
| 対象・範囲 | 対象のサイト・環境・機能、作業の範囲 |
| 作業内容 | 実施すること |
| 作業順・手順 | 順序に意味がある作業 |
| 完了条件 | 作業が終わったと判断できる結果 |
| 検証すること | 確認する動作・影響、具体的な検証方法 |
| 制約・対象外 | 守る条件、維持するもの、今回扱わないこと |
| 作業の前提・依存関係 | 着手条件、先行・並行作業、後続へ進む条件 |
| 判断が必要なこと | 未決定事項、人間の判断やレビューが必要な点 |
| 参照先 | 関連資料、仕様、手順へのリンク |

小さなIssueなら短い説明と完了条件だけでもよい。完了条件を個別に確認する場合はチェックボックスを使い、確認済みの範囲や残る条件が分かるように書く。依存関係はLinearの関連付けにも反映する。

影響範囲や設計上の難所など、担当者によらず必要な注意点を関連箇所に補う。人間レビューは、実装開始時の合意と個別の指定に従う。

### 作業結果の記録先

「決める」「設計する」「整理する」作業の結果は、Issue Descriptionに追記せず、別のドキュメントやProject Updateにまとめる。複数タスクで継続して参照する内容はProject Documentに置き、IssueやProject Updateから参照する。

Issueの完了コメントには結果の要約と反映先を残す。Descriptionは作業の説明として保ち、成果物へのリンクが必要なら参照先へ追加する。

## Project Update

現在地・残作業・次の対応が読み取れるようにする。冒頭で全体の状況を短く伝え、詳細は状態や論点に応じて整理する。

| 項目の候補 | 内容 |
| --- | --- |
| 完了・進んだこと | 主な進捗と結果 |
| 決まったこと・計画変更 | 判断や変更の要点、理由、参照先 |
| 残る確認・対応 | 完了までに必要な作業 |
| 障害・保留 | 進められない理由と再開条件 |
| 判断が必要なこと | 人間に求める判断やレビュー |
| 次に進めること | 次の作業、必要なら担当や時期 |

判断待ちと並行して続ける作業があれば区別する。長いIssueタイトルを文中に埋め込まず、短い表示名でリンクする。

## 実装結果・Workerからの報告

完了内容と検証結果を中心に、残件・未確認事項、参照先を必要に応じて補う。コミットやPRがあればリンクを添える。

Workerからの報告には、変更範囲と担当外へ影響する発見も含める。同じ報告を複数の固定テンプレートへ転記することを必須にしない。
